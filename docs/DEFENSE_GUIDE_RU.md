# DepSentry — шпаргалка для защиты

## Что это за проект?
DepSentry — веб-прототип для проверки зависимостей проекта на известные уязвимости. Он помогает увидеть проблему, понять её серьёзность и найти ссылку на рекомендацию или доступную исправленную версию.

## Как работает?
1. Пользователь загружает файл зависимостей (`package.json`, `package-lock.json`, `requirements.txt` или `pom.xml`) либо вводит список вручную.
2. JavaScript в браузере извлекает имена пакетов и точные версии.
3. Приложение запрашивает сведения у публичного сервиса OSV.dev.
4. Результаты показываются в отчёте; если сервис сообщает исправленную версию, она отображается вместе с рекомендацией.
5. Отчёт можно выгрузить в JSON или распечатать в PDF.

## Почему мы проверяем зависимости, а не весь исходный код?
Зависимости — это внешние библиотеки, которые использует проект. Уязвимость в такой библиотеке может повлиять на приложение. Проверка манифеста — более узкая и понятная задача для MVP, чем полный статический анализ исходного кода.

## Какие технологии использованы?
- HTML — структура интерфейса.
- CSS — оформление и адаптация под экран.
- JavaScript — навигация, чтение файлов, запросы к API и отображение результатов.
- OSV.dev API — поиск опубликованных сведений об уязвимостях.
- Browser local storage — локальная история сканирований.

## Что можно честно назвать ограничениями?
- Это MVP-прототип, не production-система.
- Для живой проверки нужен интернет и доступ к `api.osv.dev`.
- Проект не имеет backend, настоящей авторизации, облачного хранения и командной синхронизации.
- Результат зависит от данных OSV.dev и корректности версии зависимости.
- Если уязвимость не найдена, это не является доказательством полной безопасности.

## Как запустить без интернета?
Можно открыть интерфейс и показать навигацию, поля и документацию. Для живого запроса к OSV.dev интернет необходим. Не выдавайте демонстрационный интерфейс за подтверждение работающего live-запроса, если сеть/API недоступны.

## Если преподаватель спрашивает о GitHub-коммитах
Коммит — это зафиксированное состояние файлов с сообщением о том, что изменено. Важно сохранять понятные сообщения и делать коммиты после реальных изменений. Не нужно придумывать прошлые коммиты или утверждать, что работа выполнялась в даты, когда этого не было.
